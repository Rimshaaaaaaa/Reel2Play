# Demo claim and evidence matrix

Use this matrix while writing narration and the submission description. A feature's code or adapter existing in the repository is not proof that a live provider or external integration executed successfully.

| Topic | Safe wording without live evidence | Evidence required for a stronger claim | Avoid saying without that evidence |
|---|---|---|---|
| Muse Spark Open | "The architecture includes a Muse Spark Open provider integration." | Redacted run record showing the director call and provider/model for the recorded run | "Muse Spark Open powered this demo." |
| Muse Glimmer | "The project includes a Glimmer tester integration; this demo used [actual mode]." | Redacted tester request/result from the same recorded run | "Glimmer played and tested this game" when scripted/mock fallback ran |
| SAM 3.1 | "SAM 3.1 is an available segmentation integration; [actual fallback/status] was used here." | Successful SAM endpoint response and corresponding run evidence | "SAM 3.1 segmented the product" when fallback cut-out was used |
| Quality gates | "The application has code-defined quality gates." | Report from the exact game shown, with gate outcomes | "Every game is guaranteed bug-free." |
| Safety | Describe the specific control visible or verified in the run | Relevant test result, redacted audit event, or visible UI state | "All safety risks are eliminated." |
| Evaluation | "The harness is implemented; CI uses synthetic videos and mock responses." | Dated `report.md` and `results.json` from the 30 real, consented video run | Any customer success rate, conversion uplift, or 30-shop result before that run |
| Gallery | "The gallery page is implemented and awaits approved evaluation entries." | Gallery page populated with approved evaluated ads | "30 evaluated ads are live" while the gallery is empty |
| WhatsApp | "The project contains a WhatsApp Cloud API integration." | A current end-to-end test with the configured Meta test/business number | "WhatsApp delivery is live" without a successful current message exchange |
| Meta playable | "The builder supports a Meta playable export." | Export generated by the same demo run and inspected against current portal requirements | "The ad is approved by Meta" unless Meta actually approved it |
| Analytics | "The hosted page records anonymous play events." | Redacted event data from the deployed environment | Any fabricated engagement or sales outcome |

## Evidence handling

- Keep screenshots and logs redacted. Never capture `.env`, authorization headers, API keys, access tokens, private consent records, phone numbers, or personal data.
- Keep synthetic and real-shop runs separate in filenames and descriptions.
- A screenshot of a settings page proves configuration is present, not that the provider executed successfully.
- If a fallback ran, name the fallback. If the provider cannot be identified, say "not verified".
- If evidence conflicts with a sentence in the write-up, change the sentence rather than changing or hiding the evidence.
